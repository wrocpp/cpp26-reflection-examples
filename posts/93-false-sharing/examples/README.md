# False sharing: write contention benchmark

Companion to the wro.cpp post on false sharing. All numbers in the post come from the
CSV files here.

| File | What it is |
|---|---|
| `bench.cpp` | the benchmark: T threads each increment their own counter N times, 13 layouts |
| `run.sh` | `sh run.sh mac`, `sh run.sh docker`, `sh run.sh tls`: build, run, write results and env |
| `analyze.py` | markdown tables (median, min, max, CV, ratio to padded) from a results CSV |
| `results-mac-m2max.csv`, `results-docker-aarch64.csv` | raw rows, one per run (11 runs per cell) |
| `results-x86/`, `tables-x86.md`, `bench-run-x86.sh` | the x86-64 run: raw and filtered CSVs, noise logs, host info, assembly, driver script (see "x86-64 run") |
| `tables-*.md` | the post's tables, generated by `analyze.py` from the CSV |
| `env-*.txt` | machine, compiler, flags, load before and after, for each CSV |
| `layout_demo.cpp` | `static_assert`s on size, alignment and offsets plus a correctness-only run; the Compiler Explorer demo |
| `tls_addresses.cpp`, `tls-addresses.txt` | where `thread_local` counters of live threads sit |

Unit: wall nanoseconds per increment per thread (wall time from barrier release to the last
thread finishing, divided by the increments each thread did). Every run checks that the
counters sum to T times N.

## Notes on the kernels

- `atomic_kernel` and `plain_kernel` are `noinline` and take a reference, so every layout runs
  the same machine code. In a first version the plain loop on the packed array used a
  register-offset address and was about six times slower than the padded one at one thread.
- The plain kernel uses an `asm` memory operand and not `volatile`: GCC 16.2 on macOS folded a
  loop over a `volatile thread_local` into a single add.
- After the runs, one unneeded `#pragma GCC diagnostic` line was removed from `bench.cpp`
  (the file compiles without warnings under `-Wall -Wextra -Werror`). The GCC 16.2 assembly
  for macOS is identical before and after the edit.

## x86-64 run

A third machine: an Intel Core i7-10510U (4 cores, 2 threads each, SMT on; sibling pairs are
CPUs 0/4, 1/5, 2/6 and 3/7), run as a CI job on a runner on a shared laptop. Inside the
container: Linux 6.12, `intel_pstate` with the `powersave` governor, turbo on
(`no_turbo` is 0), 59% scaling at the start. The frequency is not fixed, so compare ratios
between machines, never nanoseconds. GCC 16.2.0 from a pinned image
(`gcc@sha256:3f73339bf0d3d64081cac3f6d9fdafc6dd4cef2b9c49e0a09f91e97cb0eb139a`, amd64),
`-std=c++23 -O2 -pthread`. On x86 `hardware_destructive_interference_size` is 64, so
"padded to HDIS" and "padded to 64" are the same layout there.

`bench-run-x86.sh` runs one repetition per process with `--no-warmup --run-base K` and
`taskset`, after one discarded warm-up. It reads the 1-minute load average before and after
each repetition and marks the repetition noisy when it ends above the benchmark's own thread
count plus one. Three configurations ran, 11 repetitions each (11 timed runs per cell):

| Config | CPUs | Threads | Result |
|---|---|---|---|
| `first4` | 0-3, one thread per core | 1, 2, 4 | 0 noisy repetitions |
| `all` | 0-7, threads 5-8 share a core through SMT | 1, 2, 4, 8 | 0 noisy repetitions |
| `percore4` | four CPUs on four cores | 4 | 25 of 25 noisy, no usable data |

A quiet-host guard ran first: the host's load average was 18.7 at the start and 10 to 20 in
bursts, and the guard waited 1180 s until the 1-minute average fell below 1.0 (it passed at
0.97, see `quiet.txt`). The 1-minute load average was still decaying from the preceding
8-thread configuration when `percore4` started, so every one of its 25 repetitions was
flagged noisy and `results-percore4.filtered.csv` holds only the header; the post does not
use it. For `first4` and `all` the filtered files equal the raw ones, and `tables-x86.md` is
`analyze.py` on the raw files. All checksums passed. The CI helper scripts that the driver
mentions (`ci/host-info.sh`, `ci/wait-quiet.sh`) are not part of this directory;
`host-info.txt` and `quiet.txt` are their output, with the runner name and id removed.

`bench-x86.s` is the assembly of the same `bench.cpp`. The atomic kernel is a loop of
`lock addq $1, (%rdi)` (unrolled by two). The plain kernel is `addq $1, (%rdi)` in a loop: a
read-modify-write of memory without `lock`, one instruction per increment for every layout.
